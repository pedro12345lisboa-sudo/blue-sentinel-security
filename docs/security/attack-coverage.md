# MITRE ATT&CK Coverage — BLUE-SENTINEL Detection Library

Which ATT&CK techniques the published rules actually detect, and — just as
important — which ones they do **not**. Everything on this page is derived
from the rule files themselves: Sigma `tags:`, YARA `meta.mitre` and the
`mitre:` field of the correlation patterns under `rules/patterns/`.

## Regenerating this matrix

The table between the markers is generated, so it can never drift away from
the rules it describes:

```bash
python scripts/development/validate_rules.py --write-docs   # refresh the block
python scripts/development/validate_rules.py --check-docs   # CI gate: fails when stale
```

CI runs the check (see `.github/workflows/ci.yml`); if you add or retag a
rule, re-run `--write-docs` and commit the result together with the rule.

## How to read it

- One row per **(tactic, technique)** pair. A technique that ATT&CK lists
  under several tactics (for example `T1078` Valid Accounts) appears once per
  tactic, exactly like the ATT&CK navigator does.
- **Coverage** lists the rule ids that fire on it: Sigma (`bs-…`), YARA
  (`EICAR_Test_File`, …) and correlation patterns (`corr-…`).
- Technique ids are validated at load time against
  `backend/app/detection/mitre.py`; a tag that is not in the catalog breaks
  the build rather than silently producing a rule nobody can explain.
- Coverage is **not** the same as detection confidence. A row means "a rule
  fires when this technique shows up in the telemetry we collect", not
  "the technique cannot succeed".

## Known gaps (honest list)

**Tactics with zero coverage** (also computed into the table above):

| Tactic | Why it is out of scope today |
|---|---|
| Resource Development | The lab has no adversary-infrastructure telemetry (accounts, domains, staging). Detecting it belongs in threat-intel feeds, not in host logs. |
| Discovery | No enumeration-heavy scenario (`whoami`/`net view`/LDAP sweeps) is generated, and process command lines alone would be far too noisy without a baseline. |
| Collection | No file-access or staging telemetry (screenshots, archives, clipboard) in the normaliser's categories. |
| Exfiltration | No large-transfer or cloud-exfil events; the network category only carries connection metadata, not volume. |
| Impact | No destructive behaviour (ransomware canary files, service stop storms) is simulated on purpose — the repository ships nothing that could damage a system. |

**Partial coverage inside the covered tactics** — the library detects a
pragmatic subset, not the whole tactic:

- *Credential Access*: password guessing (`T1110.001`) only. No dumping rules
  (`T1003`, LSASS access) — that needs EDR/sysmon process-access events the
  lab does not model.
- *Defense Evasion*: log clearing and obfuscated content only. No masquerading
  (`T1036`), timestomping (`T1070.006`) or indicator-blocking rules.
- *Lateral Movement*: RDP (`T1021.001`) only; SMB/WinRM/remote services are
  not tagged because no such events exist in the corpus.
- *Command and Control*: web-protocol traffic (`T1071.001`) and tool transfer
  (`T1105`); no DNS/ICMP tunnelling, proxy or encrypted-channel detections.
- *Persistence*: Run keys, services, scheduled tasks, cron, web shells and
  account creation. No DLL search-order hijack, bootkit or cloud
  persistence beyond access-key creation.

**Structural limitations**

- **Log-source dependent.** Every Windows rule names the event ids it needs
  (4625, 4732, 7045, 4698, 1102, 4688, Sysmon). Without those channels
  enabled the rule loads but never fires; see
  [`tuning-guide.md`](./tuning-guide.md) for the pre-flight checklist.
- **YARA scope.** The five YARA rules scan the lab's synthetic *event text*
  (`event["text"]`). The repository contains no file corpus and no malware:
  the EICAR rule uses two split halves so that no file here triggers a real
  antivirus product.
- **No malware-family rules.** Writing family-specific YARA would require
  shipping samples; out of scope for a defensive-only portfolio (see
  [`SECURITY.md`](../../SECURITY.md)).
- **Behavioural sequences** (brute force, 404 scans, SQL injection bursts)
  are handled by `rules/patterns/*.yaml`, not by single-event Sigma rules —
  they are listed in the matrix because they do carry ATT&CK tags.
- **No baseline/UEBA layer.** Detections are signature-based; "unusual" is
  expressed through allowlists and thresholds, not learned profiles. The
  tuning guide documents where each threshold lives.
